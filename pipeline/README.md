# Agentic KG Generation Pipeline

Autonomous knowledge graph generation from structured data (CSV, XML, JSON, TSV, TXT) with strict **domain ontology** compliance. Each pipeline step delegates TypeScript generation to either the [Claude Code](https://docs.anthropic.com/en/docs/claude-code) or [Codex](https://github.com/openai/codex) CLI (selected via `PROVIDER` in `.env`) and persists the resulting graph to Neo4j over MCP.

## Overview

This project implements a fully autonomous pipeline that transforms raw structured data into an ontology-compliant knowledge graph stored in Neo4j. The pipeline is:

- **Ontology-agnostic** — works with any OWL/RDF/XML ontology (EDM, FaBiO, Schema.org, etc.)
- **Format-agnostic** — accepts CSV, XML, JSON, TSV, and TXT input files
- **Domain-organized** — each dataset lives in its own directory with its own ontology and outputs
- **Prompt-driven** — every pipeline step is a bash script that sends a specification to Claude Code or Codex (whichever is set via `PROVIDER`), which generates and immediately executes TypeScript. The generated code is ephemeral (gitignored); the prompts are the source of truth.

```
prompts/<step>.sh  →  <provider CLI> "..."  →  src/generated/<provider>/<domain>/<step>.ts  →  executes  →  $DATA_DIR/output/
```

### Adding a New Domain

1. Create the directory structure: `domain-data/<your-domain>/{input,output,ontology}/`
2. Place your data files in `input/` and ontology file(s) in `ontology/`
3. Optionally create `supplementary-files/` for reference/lookup data (see [Supplementary Files](#supplementary-files))
4. Set `DATA_DIR=domain-data/<your-domain>` in `.env`
5. Run the pipeline — the ontology parser auto-discovers and handles any OWL/RDF/XML/TTL ontology

## Architecture

### Pipeline Flow

```
Input Data (CSV/XML/JSON/TSV/TXT) + optional Supplementary Files
    │
    ▼
[1] Merge ──────────── Detect formats, parse, unify into single CSV
    │
    ▼
[2] Profile ────────── Analyze column types, distributions, missing values
    │
    ▼
[3] Parse Ontology ─── Auto-discover .owl/.xml/.ttl/.rdf files, extract classes/properties
    │
    ▼
[4] Map to Ontology ── Map dataset columns → ontology classes & properties
    │                   ┌────────────────────────────────┐
    │                   │  CK #1                         │
    │                   │  Compliance score must be ≥70  │
    │                   └────────────────────────────────┘
    ▼
[5] Clean ──────────── Type coercion, dedup, null normalization
    │
    ▼
[6] Generate Graph ─── Build nodes & relationships as JSON/Cypher/Turtle
    │                   ┌─────────────────────────────┐
    │                   │  CK #2                      |
    │                   │  validation of              │
    │                   │  every node & relationship  │
    │                   └─────────────────────────────┘
    ▼
[7] Import Neo4j ───── Load graph into Neo4j via MCP tools
    │
    ▼
[8] Validate ───────── Post-import audit against ontology constraints
                        ┌─────────────────────────────┐
                        │  CK #3                      |
                        │  Generates automated fix    │
                        │  queries for violations     │
                        └─────────────────────────────┘
    │
    ▼
[8]B Validate ───────── Validation against pre-authored SHACL
                        ┌─────────────────────────────┐
                        │  CK #4                      |
                        │  Validates against pre-     │
                        │  authored SHACL shapes      │
                        └─────────────────────────────┘
```

### Prompt-Driven Code Generation

Each pipeline step follows the same pattern:

1. A bash script in `prompts/` contains a detailed specification
2. The script invokes either `claude -p "<spec>"` or `codex exec --full-auto "<spec>"` depending on `PROVIDER`
3. The provider generates TypeScript to `src/generated/<provider>/<domain>/<step>.ts`
4. The TypeScript executes immediately, reading inputs and writing outputs
5. Results go to `$DATA_DIR/output/<provider>/` as JSON, CSV, Cypher, or Turtle

To change how a step works, **edit the prompt in `prompts/<step>.sh`**, not the generated TypeScript. The generated code will be overwritten on the next run.

### Three-Gatekeeper Compliance

The pipeline enforces strict ontology compliance at three checkpoints:

1. **Mapping (Step 4)** — Only ontology terms are allowed. Every dataset column must map to a recognized class or property. Unmapped columns are flagged. A compliance score is computed; the pipeline halts if it falls below 70/100.

2. **Generation (Step 6)** — Every node and relationship is validated in-flight against the ontology. Custom classes or properties not present in `ontology-structure.json` are rejected. The output includes compliance metadata.

3. **Validation (Step 8)** — After import into Neo4j, a full audit runs against the live graph. Violations are detected (invalid labels, missing required properties, wrong relationship types) and automated Cypher fix queries are generated.

Compliance scoring: **A** (95-100), **B** (80-94), **C** (70-79), **D** (60-69), **F** (<60 — pipeline blocked).

### Neo4j MCP Integration

The import and validation steps communicate with Neo4j through an MCP (Model Context Protocol) server. The MCP server is a separate project and provides these tools:

| Tool                               | Purpose                                       |
| ---------------------------------- | --------------------------------------------- |
| `mcp__neo4j__execute_cypher`       | Run arbitrary Cypher queries                  |
| `mcp__neo4j__create_nodes`         | Batch-create nodes with labels and properties |
| `mcp__neo4j__create_relationships` | Batch-create relationships                    |
| `mcp__neo4j__run_bulk_import`      | Import graph from JSON file                   |
| `mcp__neo4j__get_schema`           | Inspect database schema                       |
| `mcp__neo4j__get_statistics`       | Node/relationship counts                      |
| `mcp__neo4j__clear_database`       | Wipe database (requires confirmation)         |

Test connectivity: `bash lib/check-neo4j-connection.sh` or CLI option 14.

## Pipeline in Depth

### Step 1: Merge Datasets

**Script:** `prompts/merge-datasets.sh`

Scans `$DATA_DIR/input/` for all data files and unifies them into a single `dataset-merged.csv`. Supports multiple input formats:

- **CSV/TSV** — parsed with PapaParse
- **TXT** — tab-delimited or other delimiter with auto-detection; handles headerless files (e.g., GeoNames exports) by assigning positional column names
- **JSON/JSONL** — loaded directly or streamed line-by-line
- **XML** — SAX-based streaming parser for memory efficiency (critical for multi-GB files like the 4.7GB DBLP XML)

The merge step auto-detects which strategy to use:

| Strategy              | When                              | Example                                            |
| --------------------- | --------------------------------- | -------------------------------------------------- |
| **Union**             | Files share the same schema       | Multiple TXT files with identical columns          |
| **Join**              | Files share a foreign key         | `artists.csv` + `artworks.csv` joined on artist ID |
| **Merge**             | Files represent different aspects | Side-by-side column combination                    |
| **Single Conversion** | Only one input file               | Converting a large XML to CSV                      |

For large files (>100MB), streaming is enforced — files are never loaded entirely into memory. XML parsing uses SAX with chunk-based processing (accumulate N records, flush to disk, continue).

The merge step also discovers **supplementary files** in `$DATA_DIR/supplementary-files/` (if the directory exists) and creates an index at `supplementary-files-index.json`. Supplementary files are NOT merged into the main dataset — they are reference/lookup data used by downstream steps.

**Output:** `dataset-merged.csv`, `merge-report.json`, `supplementary-files-index.json` (if applicable)

### Step 2: Profile Dataset

**Script:** `prompts/profile-data.sh`

Analyzes the merged CSV to produce a structural profile:

- Total rows and columns
- Inferred data types per column (string, numeric, date, boolean)
- Missing value counts and percentages
- Unique value counts per column
- Sample values (first 5 unique per column)
- Basic statistics for numeric columns (min, max, mean)

If supplementary files exist, the profiler cross-references code columns against supplementary lookup tables, noting which columns have matching reference data.

**Output:** `dataset-profile.json`

### Step 3: Parse Ontology

**Script:** `prompts/parse-ontology.sh`

Auto-discovers all ontology files in `$DATA_DIR/ontology/` (`.owl`, `.xml`, `.ttl`, `.rdf`, `.n3`, `.jsonld`) and parses them into a unified JSON structure. This is the **single source of truth** for all downstream compliance checks.

The parsed output includes:

- All classes with their hierarchy (superclasses, equivalent classes)
- All properties (object and data) with domain/range constraints
- Namespace declarations
- Required properties per class
- Ontology metadata (title, version, authors)

**Output:** `ontology-structure.json`, `ontology-mapping-guide.json`, `ontology-quick-reference.json`

### Step 4: Map to Ontology (Gatekeeper #1)

**Script:** `prompts/create-mapping.sh`

Maps each dataset column to an ontology class and property. The mapping reads classes, properties, and namespaces from `ontology-structure.json` — nothing is hardcoded. If supplementary files exist, they are loaded to provide domain context (e.g., understanding that a column contains feature codes by matching values against a feature code lookup table).

For each column, the mapping determines:

- Which ontology class the column belongs to
- Which ontology property represents the column's data
- The expected data type (from the ontology's range constraints)
- Whether the column maps to a node property or a relationship

Columns that cannot be mapped are flagged. A compliance score is computed. If the score is below 70, the pipeline halts and requires review.

**Output:** `mapping-strategy.json`, `mapping-compliance-report.json`

### Step 5: Clean Data

**Script:** `prompts/clean-data.sh`

Cleans the dataset based on both general data quality rules and ontology constraints:

- Remove exact duplicate rows
- Trim whitespace, normalize null representations
- Type coercion based on ontology data property ranges (e.g., `xsd:integer` → parse to number, `xsd:date` → ISO format)
- Validate domain/range constraints from the ontology
- Validate coded values against supplementary lookup tables (if available)
- Remove rows that violate critical constraints

Large datasets are processed in chunks (5,000 rows).

**Output:** `dataset-cleaned.csv`, `cleaning-report.json`

### Step 6: Generate Knowledge Graph (Gatekeeper #2)

**Script:** `prompts/generate-graph.sh`

Transforms the cleaned data into a knowledge graph. Produces three output formats:

- **JSON** — nodes and relationships as structured objects for MCP import
- **Cypher** — Neo4j import script with `CREATE` and `MERGE` statements
- **Turtle (TTL)** — RDF serialization using ontology namespaces

Every node and relationship is validated against the ontology during generation. If supplementary files exist, they are used for enrichment — resolving coded values to human-readable labels, creating reference nodes from lookup tables, and adding relationships between main data and reference entities (all ontology-compliant).

For large datasets, the generator uses streaming architecture with O(n) complexity — a first pass writes nodes and buffers relationships to a temp file, then a second pass writes relationships from the buffer.

**Output:** `graph-data.json`, `graph-import.cypher`, `graph-data.ttl`, `graph-stats.json`

### Step 7: Import to Neo4j

**Script:** `prompts/import-to-neo4j.sh`

Loads the generated graph into Neo4j using the MCP server. This step:

- Clears existing data (with confirmation)
- Creates uniqueness constraints and indexes
- Batch-imports nodes and relationships
- Verifies import counts match generation stats

**Output:** `neo4j-import-report.json`

### Step 8: Validate Compliance (Gatekeeper #3)

**Script:** `prompts/validate-ontology.sh`

Runs a post-import audit against the live Neo4j graph. All validation rules are built dynamically from `ontology-structure.json` — no class names, properties, or namespaces are hardcoded.

Checks include:

- Node labels match ontology classes
- Relationship types match ontology object properties
- Required properties are present
- Property values conform to expected types
- Namespace consistency

Violations are categorized by severity and automated Cypher fix queries are generated where possible.

**Output:** `validation-report.json`, `validation-report.txt`, `violations-details.json`, `fixes.cypher`

## Getting Started

### Prerequisites

- Node.js 20+
- One of these CLIs on `PATH`, matching `PROVIDER` in your `.env`:
    - [Claude Code](https://docs.anthropic.com/en/docs/claude-code) — `claude` (default)
    - [Codex](https://github.com/openai/codex) — `codex` (or set `CODEX_BIN` to its absolute path)
- Neo4j 5+ (for import and validation steps)

### Setup

```bash
# Clone the repository
git clone <repo-url>
cd agentic-kg-artifact-pipeline

# Install dependencies
npm install

# Create configuration
cp .env.example .env
```

Edit `.env` to set your domain and Neo4j connection:

```env
DATA_DIR=domain-data/cultural-moma
NEO4J_URI=bolt://localhost:7687
NEO4J_USER=neo4j
NEO4J_PASSWORD=your_password
NEO4J_DATABASE=neo4j
```

### Download Data

Download the dataset for your chosen domain (see [Datasets](#datasets)) and place files in the appropriate directories:

```bash
# Example: MoMA
domain-data/cultural-moma/input/artists.csv
domain-data/cultural-moma/input/artworks.csv
domain-data/cultural-moma/ontology/edm.owl

# Example: DBLP
domain-data/scientific-dblp/input/dblp.xml
domain-data/scientific-dblp/input/dblp.dtd
domain-data/scientific-dblp/ontology/fabio.xml

# Example: GeoNames (with supplementary files)
domain-data/geospatial/input/DE.txt
domain-data/geospatial/input/FR.txt
# ... more country files
domain-data/geospatial/ontology/geo.ttl
domain-data/geospatial/supplementary-files/countryInfo.txt
domain-data/geospatial/supplementary-files/admin1CodesASCII.txt
domain-data/geospatial/supplementary-files/featureCodes_en.txt
```

### Run

```bash
# Interactive CLI
./main.sh

# Or run the full pipeline directly
npm run pipeline
```

## Supplementary Files

Some domains include **supplementary reference data** — lookup tables, code definitions, taxonomies, or metadata that enriches the pipeline without being part of the primary dataset. Place these in `$DATA_DIR/supplementary-files/`.

```
domain-data/<domain>/
├── input/                    # Primary data files (merged into dataset)
├── supplementary-files/      # Reference/lookup data (NOT merged)
│   ├── countryInfo.txt       #   Country code → name, population, area
│   ├── featureCodes_en.txt   #   Feature code → description, category
│   └── admin1CodesASCII.txt  #   Admin code → division name
└── ...
```

Supplementary files are **not merged** into the main dataset. Instead, the pipeline uses them at multiple stages:

| Step               | How Supplementary Files Are Used                                      |
| ------------------ | --------------------------------------------------------------------- |
| **Merge (1)**      | Discovered and indexed to `supplementary-files-index.json`            |
| **Profile (2)**    | Cross-referenced to identify code columns with matching lookup tables |
| **Mapping (4)**    | Loaded for domain context — helps understand what columns contain     |
| **Cleaning (5)**   | Used to validate coded values against reference data                  |
| **Generation (6)** | Used for enrichment — resolve codes to labels, create reference nodes |

This is fully backwards compatible: domains without a `supplementary-files/` directory (like MoMA and DBLP) are unaffected.
